# 架构说明 · 这个软件是怎么工作的

> 面向想读懂本项目源码的读者。读完本文 + 对照 `src/todo.js`(60 行),即可理解本项目 80% 的设计。

## 1. 整体架构:三个进程,各司其职

```
┌─────────────────┐         ┌──────────────────┐         ┌─────────────────┐
│  QQ + NapCat    │         │   msg2todo       │         │  本地大模型      │
│  (QQ-napcat)    │         │   (Electron)     │         │   (Python)      │
│                 │         │                  │         │                 │
│  QQ 消息 ──────►│ WS:3001 │                  │ HTTP    │                 │
│                 │────────►│  待办助手        │────────►│  Qwen2.5-3B     │
│                 │         │                  │         │                 │
│                 │         │  看板 :8000 ◄────│ HTTP    │                 │
│                 │         │                  │         │                 │
│                 │         │  推送 ───────────│────────►│  Bark / PushDeer│
└─────────────────┘         └──────────────────┘         └─────────────────┘
```

**为什么拆成三个进程?**

- QQ 机器人必须挂在 QQ 客户端里(NapCat 是 QQ 的插件)
- 大模型吃显存,独立进程挂了不影响主程序
- 主程序(Electron)负责界面和调度

**进程间怎么通信?** 全部是网络协议:

| 通道 | 协议 | 方向 |
|------|------|------|
| QQ → 主程序 | WebSocket | NapCat 主动连 `ws://127.0.0.1:3001` |
| 主程序 → 大模型 | HTTP | OpenAI 兼容接口 |
| 主程序 → 手机 | HTTP | Bark / PushDeer 推送接口 |
| 浏览器 → 主程序 | HTTP + SSE | 看板 API + 实时推送 |

## 2. 核心管线:一条消息的旅程

整个软件的心脏是 `src/todo.js` 的 `handleIncoming()`。任何来源的消息都走同一条管线:

```
消息进来
   │
   ▼
① 记录原始消息 ──────────────► SQLite messages 表(留档,方便调试)
   │
   ▼
② 关键词预过滤 ── 不含"提醒/记得/待办"等词 ──► 直接丢弃(省钱)
   │ 包含
   ▼
③ 智能提取 ──► 调大模型(LLM)
   │              │ 失败/超时
   │              ▼
   │         降级到本地规则(中文时间解析)
   │
   ▼
④ 判断结果:isTodo? ── 否 ──► 丢弃(闲聊不产生待办)
   │ 是
   ▼
⑤ 写入待办 ──────────────► SQLite todos 表
   │
   ▼
⑥ 触发推送 ──────────────► Bark/PushDeer(新待办通知)
   │
   ▼
⑦ 可选:回复发送者 ────────► 通过 WS 让 NapCat 发消息(默认关闭)
```

**关键设计:LLM 优先 + 规则兜底**。大模型聪明但可能超时/报错,失败时自动降级到本地规则——这叫**故障转移(failover)**,是保证可用性的常用手段。

## 3. 各模块职责

| 文件 | 职责 | 用到的知识 |
|------|------|-----------|
| `src/onebot.js` | QQ 接入:WebSocket 服务端、协议解析、消息去重、@检测 | 网络协议、并发 |

| `src/db.js` | 数据库:建表、增删改查、自动迁移 | SQL、SQLite |
| `src/web.js` | 看板服务:HTTP API + SSE 实时推送 + 静态文件 | HTTP、SSE |
| `src/notify.js` | 手机推送 + 定时提醒(每 30 秒检查) | 定时器、HTTP |

## 4. 关键设计决策

### 4.1 为什么用「反向 WebSocket」?

```
正向:我们主动连 NapCat ──► NapCat 得开端口,配置麻烦
反向:NapCat 主动连我们 ──► 我们只开一个端口,插件端填地址就行
```

服务端永远是被连的那个——就像「你打给我」比「我打给你」简单。

### 4.2 为什么过滤"自己的消息"?

机器人回复的消息也会被 NapCat 收到 → 如果不过滤 → 回复又被当成新消息 → 又生成待办 → 又回复……**死循环**。所以 `onebot.js` 里有一行:

```js
if (senderId === selfId) return;  // 自己的消息不处理
```

这是所有机器人系统的**防循环基本功**。

### 4.3 为什么用 SSE 而不是轮询?

看板要实时更新。两种做法:

- **轮询**:浏览器每 3 秒问一次"有新数据吗?" → 浪费请求
- **SSE**:服务器有变化时**主动推**给浏览器 → 一条连接,实时且省资源

### 4.4 时区问题(最隐蔽的坑)

数据库存的是 **UTC 时间**(全球统一),但用户说的是"明天下午3点"(北京时间)。所以:

- 存的时候:北京时间 → 转成 UTC 存
- 显示的时候:UTC → 转回北京时间显示

`src/time.js` 就是干这个的。**所有涉及时间的系统都要处理时区**,这是经典面试题。

### 4.5 数据库自动迁移

加了新功能(提前提醒)需要新字段,但老数据库没有。`db.js` 启动时检查:

```js
if (!todoCols.includes('notified_adv_at')) {
  db.exec('ALTER TABLE todos ADD COLUMN notified_adv_at TEXT');
}
```

老用户升级后**不用手动改数据库**,自动补字段。这叫**数据库迁移(migration)**。

## 5. 完整走一遍:朋友发消息到推送

```
1. 朋友 QQ 发:"明天下午3点提醒我交高数作业"
2. NapCat 收到 → 通过 WebSocket 发到 ws://127.0.0.1:3001
3. onebot.js 收到 JSON → 解析出:发送者、群/私聊、消息文本、是否@我
4. 私聊 → 进入 todo.js 管线
5. 关键词检查:含"提醒" → 通过
6. 调大模型 → 返回 {isTodo:true, title:"交高数作业", dueAt:"2026-10-07T15:00:00+08:00"}
7. 写入 todos 表(UTC 存储:2026-10-07T07:00:00Z)
8. notify.js 触发 → Bark 推送到手机:"📝 新待办:交高数作业 · 明天 15:00"
9. 30 秒后检查器发现:距到期 59 分钟 → 进入提前提醒窗口
10. 再推一条:"⏰ 待办即将到期:交高数作业 · 约 1 小时后到期"
11. 到 15:00 → 再推:"⏰ 待办已到期:交高数作业"
```
