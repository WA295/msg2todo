# 架构说明 · 这个软件是怎么工作的

> 面向想读懂本项目源码的读者。读完本文 + 对照 `src/todo.js`(123 行),即可理解本项目 80% 的设计。
>
> ⚠️ **2026-10 修订**:原版本把架构画成"三个进程 / 主程序是 Electron / 看板 :8000 / 本地 Qwen2.5-3B",
> 那描述的是**开发期的早期形态**,与线上真实运行方式已经不一致。本文已按实际实现重画。

## 1. 整体架构:一个 Node 主进程 + 一个 QQ 侧进程

```
┌────────────────────┐   反向 WS :3001   ┌──────────────────────────────────┐
│ QQ 客户端 + NapCat │ ────────────────► │  iTodo 主进程(Node.js)          │
│ (systemd: napcat)  │                   │  单进程,零原生依赖                │
│                    │ ◄──────────────── │                                  │
│  公共号 / 学生自建 │   send_private    │  ├─ OneBot v11 服务端             │
└────────────────────┘                   │  ├─ 消息→待办核心管线 todo.js    │
                                         │  ├─ LLM(OpenAI 兼容,可选)      │
┌────────────────────┐                   │  │   └─ 失败降级:本地中文规则     │
│ 云 LLM(可选)      │ ◄─── HTTP ─────── │  ├─ SQLite(node:sqlite, WAL)     │
│ DeepSeek/Qwen/…    │                   │  ├─ 10 个定时提醒器               │
└────────────────────┘                   │  ├─ Express API + SSE + 静态页    │
                                         │  └─ 推送:Bark/PushDeer/WebPush    │
┌────────────────────┐   HTTP(S) :8080   │                                  │
│ 浏览器 / 安卓 App  │ ◄───────────────► │  Electron 桌面版只是"可选本地壳": │
│ / 桌面版 / PWA     │   SSE 实时推送    │  它内嵌同一个 src/server.js       │
└────────────────────┘                   └──────────────────────────────────┘
```

**和早期设计的差别:**

| 早期(原文档) | 现在(实际) |
|---|---|
| Electron 是主程序 | **Node 主进程**是主程序;Electron 只是可选桌面壳,内嵌同一个 `src/server.js` |
| 看板端口 :8000 | **:8080**(`WEB_PORT`) |
| 本地 Python 大模型 Qwen2.5-3B | **云端 OpenAI 兼容 API**(DeepSeek 等),未配置则纯规则模式 |
| 三个进程 | 实际是**两个**(主服务 + NapCat);NapCat 是 QQ 客户端插件,必须独立 |

**进程间怎么通信?** 全是网络协议:

| 通道 | 协议 | 方向 |
|------|------|------|
| QQ → 主程序 | WebSocket(反向) | NapCat 主动连 `ws://127.0.0.1:3001` |
| 主程序 → 大模型 | HTTP(OpenAI 兼容) | 可选;不配则走本地规则 |
| 主程序 → 手机 | HTTP | Web Push / Bark / PushDeer |
| 浏览器/App → 主程序 | HTTP + SSE | REST API + 实时推送 |

## 2. 核心管线:一条消息的旅程

整个软件的心脏是 `src/todo.js` 的 `handleIncoming()`。任何来源的消息(QQ 私聊/群聊、App 内与机器人对话)都走同一条管线:

```
消息进来
   │
   ▼
① 记录原始消息 ──────────────► SQLite messages 表(留档,排查用)
   │
   ▼
② 指令识别 ── 命中"课表/番茄/天气/倒计时/快递…" ──► 直接回复,不进待办管线
   │ 未命中
   ▼
③ 关键词预过滤 ── 不含"提醒/记得/待办"等词 ──► 直接丢弃(省 LLM 调用)
   │ 包含
   ▼
④ 智能提取 ──► 调 LLM(OpenAI 兼容)
   │              │ 失败/超时/未配置
   │              ▼
   │         降级到本地规则(src/rules.js 中文时间解析)
   ▼
⑤ 判断 isTodo? ── 否 ──► 丢弃(闲聊不产生待办)
   │ 是
   ▼
⑥ 写入待办 ──────────────────► SQLite todos 表(owner = 消息归属人)
   │
   ▼
⑦ 触发推送 ──────────────────► Web Push / Bark / PushDeer / QQ 私聊
   │
   ▼
⑧ 可选:回复发送者 ──────────► REPLY_CONFIRM=true 才回(默认静默)
```

**关键设计:LLM 优先 + 规则兜底**。大模型聪明但可能超时/报错,失败时自动降级到本地规则——这叫**故障转移(failover)**,是保证可用性的常用手段。这也是为什么 `LLM_API_KEY` 没配时系统依然可用。

## 4. 关键设计决策

### 4.1 为什么用「反向 WebSocket」?

```
正向:我们主动连 NapCat ──► NapCat 得开端口,配置麻烦
反向:NapCat 主动连我们 ──► 我们只开一个端口,插件端填地址就行
```

服务端永远是被连的那个——就像「你打给我」比「我打给你」简单。

**代价**:`config.onebot.token` 是这样的弱校验——**本机回环连接完全免令牌**
(`src/onebot.js` 的 `isLoopback` 判断)。这在同机部署下是合理取舍,但如果 3001 暴露到公网,
就必须依赖令牌;而令牌曾经明文写在文档和前端帮助页里(已修)。

### 4.2 为什么过滤"自己的消息"?

机器人回复的消息也会被 NapCat 收到 → 如果不过滤 → 回复又被当成新消息 → 又生成待办 → 又回复……**死循环**。
所以 `onebot.js` 里有防循环判断,并且**个人机器人模式要特意放行自己的消息**(学生给自己/文件传输助手发指令是有意的)。

### 4.3 为什么用 SSE 而不是轮询?

看板要实时更新。两种做法:

- **轮询**:浏览器每 3 秒问一次"有新数据吗?" → 浪费请求
- **SSE**:服务器有变化时**主动推**给浏览器 → 一条连接,实时且省资源

注意实现细节:前端有 30 秒轮询**兜底**(SSE 断了也能恢复),`sw.js` 是**纯 push、没有 fetch 缓存**,
所以"离线可用"这一条并不成立。

### 4.4 时区问题(最隐蔽的坑)

数据库存的是 **UTC 时间**(全球统一),但用户说的是"明天下午3点"(北京时间)。所以:

- 存的时候:北京时间 → 转成 UTC 存
- 显示的时候:UTC → 转回北京时间显示

`src/time.js` 就是干这个的。**所有涉及时间的系统都要处理时区**,这是经典面试题。
另外注意:.env 里的 `TZ=Asia/Shanghai` 是**必须**的,它同时影响 `nowLabel()` 喂给 LLM 的时间参考。

### 4.5 数据库自动迁移

加了新功能(提前提醒)需要新字段,但老数据库没有。`db.js` 启动时检查:

```js
if (!todoCols.includes('notified_adv_at')) {
  db.exec('ALTER TABLE todos ADD COLUMN notified_adv_at TEXT');
}
```

老用户升级后**不用手动改数据库**,自动补字段。这叫**数据库迁移(migration)**。

> 反面:迁移只有"加列"。如果将来要删列/改类型/改语义,这套机制不够用,需要引入版本号 + 显式迁移脚本。

### 4.6 多用户隔离靠 `owner` 字符串

所有业务表都带 `owner` 字段,形如 `qq:<QQ号>`(机器人自己是 `'bot'`)。
鉴权中间件(`src/web.js` 的 `app.use('/api', …)`)解析出 `req.user.owner` 后,
每个接口再自己做 `if (!req.user.isAdmin && row.owner !== req.user.owner) return 403`。

**这是本设计最脆弱的地方**:隔离是**每个接口手写**的,不是数据库层的行级安全,
一旦某个新接口忘了写这行判断,就会越权。历史上有几个接口就是这么处理的。

## 5. 完整走一遍:朋友发消息到推送

```
1. 朋友 QQ 发:"明天下午3点提醒我交高数作业"
2. NapCat 收到 → 通过 WebSocket 发到 ws://127.0.0.1:3001
3. onebot.js 收到 JSON → 解析出:发送者、群/私聊、消息文本、是否@我
4. 私聊 → 进入 todo.js 管线
5. 关键词检查:含"提醒" → 通过
6. 调大模型 → 返回 {isTodo:true, title:"交高数作业", dueAt:"2026-10-07T15:00:00+08:00"}
7. 写入 todos 表(UTC 存储:2026-10-07T07:00:00Z)
8. notify.js 触发 → Web Push / Bark 推送到手机:"📝 新待办:交高数作业 · 明天 15:00"
9. 30 秒后检查器发现:距到期约 60 分钟 → 进入提前提醒窗口
10. 再推一条:"⏰ 待办即将到期:交高数作业 · 约 1 小时后到期"
11. 到 15:00 → 再推:"⏰ 待办已到期:交高数作业"
```

去重靠 `todos` 表尾部的 `notified_at` / `notified_adv_at` / `notified_d3/d1/h3` 字段。
